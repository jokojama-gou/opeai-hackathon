# 今回のハッカソンでのAIDD-Lite参照方針

2026-09-11。状態: 今回の依頼で明示された参照導入方針を反映。AIDD-FWの全面採用ではない。

## 目的と適用範囲

今回は2人で開発するハッカソンである。互いの作業内容、判断理由、検証結果、次の作業が分かり、それぞれが使うAIにも引き継げる共通コンテキストを作る。AIDD-FWへの準拠や文書量を成果にせず、共有と検証に役立つ原則だけをAIDD-Liteとして使う。

固定的な役職、2人の合意を必須にする承認体制、詳細なチーム運営ルールは追加しない。分担が必要な作業では対象と完了条件を明確にし、具体的な担当はその作業で決める。担当の記載や次の作業候補は、実行許可やAIへの自動委任を意味しない。

## 採用する原則と最小限の使い方

以下は今回用に限定した運用原則として採用する。AIDD-FWの関連手順一式を採用するものではない。Story・GWT・ADRを全作業に強制せず、小さな表記修正には差分と必要な確認だけでよい。

| 原則 | 今回の使い方 |
|---|---|
| 人とAIの意思決定範囲を分ける | 製品の意味・MVP・採用方式などの未決定をAIが確定しない。AIは現在の依頼内の読解・整理・変更・確認を進め、判断に依存する部分だけ確認する。既存の決定は再質問しない |
| Vertical Slice | 実装を分けるときは、利用者が確認できる振る舞いと完了条件が一まとまりになる単位を使う。未確定MVPの実装やUI/API/DBの一括準備を要求しない |
| StoryとGiven/When/Then | 利用者・目的・価値を短く共有し、事前条件・操作や出来事・期待結果を記述する。未決定の期待結果は提案と明記し、方式や数値を創作しない |
| D/S/O/Vから証拠までの追跡 | 製品に関係する作業は、該当D/S/OとVから受入条件または観測項目、テスト・結果・証拠へリンクする。既存IDを維持し、Issue番号を前提とする別体系は導入しない |
| SSoTと明示的リンク | 詳細は該当の正本に一度だけ記録し、相手と各AIにはリンクを渡す。会話履歴や個人PCだけを前提にしない。編集は依頼で許可された文書に限る |
| ローカル優先の検証 | 変更に必要な確認をローカルで行い、実行条件と結果を残す。ローカル成功と製品動作・別環境での成功を区別し、未実施は未実施と書く |
| 重要な技術判断だけADR化 | 採用方式や後続設計に影響する選択を、背景・候補・採否・理由・影響・関連資料とともに、許可された時に記録する。通常の作業記録や全保留事項をADRにしない |

### 作業を渡すとき

現在地はWORKFLOW、詳細な手順・結果は各正本を参照する。分担するときは変更対象と受け渡す成果を明示し、同じファイルの競合を避ける。相手の変更を上書きしない。各AIには共通資料に加え、今回の依頼範囲を渡す。固定的な分担や承認ゲートを増やさない。

次は短い記録の例であり、全欄の記入を必須にする新しい様式ではない。既存のWORKFLOW・VALIDATIONの様式で足りる場合はそちらを使う。

```text
目的・今回の対象／対象外:
関連資料・D/S/O/V（製品に関係する場合）:
担当範囲・受け渡す成果:
完了条件・確認方法:
判断と理由／結果と証拠へのリンク:
未決定・未検証／次の作業候補:
```

Storyは「誰が・何をしたい・何のために」、受入条件は「Given: 前提／When: 操作・出来事／Then: 観測できる結果」で表す。検証では、確定した振る舞いの受入条件と、未知の性能を測る観測項目を分ける。O10未決定の数値を合格基準にしない。未実行のテストや存在しない証拠をリンク先として作らない。

## 採用しないもの

- `/aidd-setup`、`aidd-framework/`のコピー、GitHub Labels・Issue Template・GitHub Actions Workflow・branch protectionの自動設定。
- 全問題の即時解決、全不明点の事前質問、全質問の`docs/questions`記録。
- 1%スキルトリガー、Claude固有のモデル選定、特定承認語の強制、codegraphの強制。
- 全階層・全ゲート・監査ログ、技術スタックの未定禁止、`1 PR = 1 Epic`の強制。

AIDD-FWのREADMEと現行パイプライン、Storyの管理場所と配布テンプレートなどには調査時点で不整合があった。外部資料を丸ごと作業規則として使わず、上の採用範囲とこのリポジトリの正本で判断する。

## 現在地と未決定の扱い

今回の成果は共通コンテキストの文書反映。2人の実利用や新しい会話でのAIの遵守を実証したものではない。MVP・製品技術・処理場所は未決定のまま維持する。

次の技術作業候補はV01/V03/V04の複数録音対応付け検証である。文書整備の目的や必須の進行経路にはせず、具体的な検証順序・分担・実行は次の依頼で決める。録音・実音声処理を開始せず、既存の音声検証計画も実行許可として扱わない。

不明事項は必要なときに次の分類で整理する。全不明点の収集や事前解決は要求しない。

| 分類 | 扱うもの |
|---|---|
| HUMAN-DECISION | 人が決める必要がある方針・範囲。依存する作業に入る時に具体案とともに確認する |
| VALIDATION | 測定・動作確認で確かめる仮説。文書の記述だけで成功扱いにしない |
| IMPLEMENTATION | 許可された作業に必要な実装・環境上の不足。発見だけで実装を開始しない |
| LATER | 現在の目的に不要な事項。必要になる時点で再検討する |
