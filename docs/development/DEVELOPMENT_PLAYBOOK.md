## 使い始める

ユーザーは「目的・今回頼む範囲・期待する結果」を伝えればよい。AIは読める情報を調べ、不足だけを推奨案付きで確認する。様式の全欄をユーザーに埋めさせない。

1. 現在の依頼を相談／調査／設計／実装／修正／検証／レビューのどれかに位置付け、成果物と停止点を短く示す。
2. 下の表から必要な参照元だけ読む。変更済みファイルは編集直前に最新版を確認する。
3. 関連する未決定に依存する部分だけ保留し、独立してできる作業を進める。
4. 完了条件に対して結果と証拠を照合し、決定・未検証・次の判断を記録する。

## 進行とスコープ管理

AGENTS.mdから移した有効な手順です。開始・範囲変更・調査・段階移行・脱線時に適用します。

- 新しい作業の開始時と範囲変更時に「目的／段階／成果物・完了条件／許可範囲・対象外」を短く示す。継続中の細かな修正ごとには繰り返さない。重要な意図が不明な場合だけ、必要な問いに絞って確認し、回答に依存する作業を止める。独立した整理は続ける。
- 段階は探索（全体像と未知）、計画（優先順位と範囲）、設計（方式と検証方法）、実装（変更と検証）で区別する。行き来してよいが、了承済みの範囲を越えて段階を移さない。具体的に依頼された実装・検証に必要な読解や設計まで、個別承認に分解しない。
- 調査のまとまりごとに「答える問い／今の目的との関係／終了条件」を短く示す。検索1回ごとの説明は不要。現在の問いに不可欠でない発見は保留事項に残し、追加調査や試作を主作業にしない。
- 「ok」は、会話で明確に提示した範囲への了承として扱う。計画への了承を方式採用・実装・追加の準備依頼などへ拡張しない。複数の提案のどれを了承したかで行動が変わる場合だけ確認する。AIの「次の作業」や既存ツールの存在は続行の許可にならない。
- 範囲内の読解・整理・草案作成・修正・検証は自律的に進める。目的や優先順位の変更、未了承の段階移行・範囲拡大、新たなユーザー負担が必要なら、理由と具体的な成果物・範囲を示して確認する。同じ了承は取り直さない。
- 目的との関係を「将来必要だから」としか説明できない、別の問いが主作業になった、またはユーザーから意図のずれを指摘された場合は、その枝を止める。「元の目的／ずれた点／保留する作業／戻る次の一手」を示す。成果物は勝手に削除せず、範囲内で全体整理に戻れるなら戻る。
- 開発開始・段階変更時には、AIが段階・許可範囲・対象外・成果物・完了条件の更新案を示す。ユーザーが明示した決定は再承認を求めず反映し、未決定だけ確認する。基本ルールは継続し、計画段階の制限は了承された範囲で更新する。文書の更新は許可された変更先に限る。
- 特定の作業分野を一律に禁止・保留しない。調査・検証・実装・環境変更は、現在の目的・優先順位・依頼範囲に照らして進める。進行ルールの文書更新への了承を、別の作業の実行許可にはしない。
- 本規則だけで脱線の完全防止を保証しない。完了時は成果・未確定・未検証を区別し、次の提案を実行済み・採用済みにしない。

## 共通の入力・出力

以下はAIが整理する項目。小さな依頼では1〜2文で足りる。共通事項を各作業へ全文複製しない。

```text
目的／作業区分:
変更してよい場所・内容／対象外:
参照した方針・仕様（製品に関係する場合はD/S/O）:
確定した前提／未決定と判断者:
完了条件／確認方法／作業を返す条件:
```

結果は[WORKFLOWの結果報告様式](WORKFLOW.md)を使う。記録ID・対象版・実行条件・人間の判断・観測・証拠・推測・未検証・次の判断を区別し、実音声や派生情報を記録へ混ぜない。

## 作業別の手順

各節に使用場面、入力、参照元、道具の選定、手順、判断境界、検証、完了条件、記録先をまとめる。道具の利用可否は[機能確認表](CODEX_OPERATING_GUIDE.md)で確認する。

### 1. 相談・調査

- **入力・参照**：知りたい問い、何の判断に使うか。製品判断なら正本と該当U/O、それ以外は関係する調査資料だけ。
- **道具・手順**：ローカル検索・読解で既知を整理→不足だけWeb一次情報で確認→結論、選択肢、根拠の差を示す。引用元の日付・対象モデル・確認範囲を残す。問いが変わる追加調査は保留する。
- **判断境界**：調査の依頼を方式採用・試作・外部データ送信へ拡張しない。推奨案は第一候補と理由を示し、重要な違いがある代替案だけ添える。
- **検証・完了**：問いに答える根拠があるか、反例・限界・未知が分かるかを照合。記事の閲覧と手元の動作確認を混同しない。終了条件が満たされたら探索を止める。
- **記録先**：結論と必要な判断をWORKFLOW。長い調査は許可された文書へ分離し参照する。独立調査フォルダへの保存は別途変更範囲を確認。

### 2. 仕様相談・設計

- **入力・参照**：達成したい利用者の体験、関連D/S/O、対象範囲、既存の設計・コード（存在する場合）。
- **道具・手順**：文書・コード検索→確定方針を振る舞いへ対応付け→正常・境界・失敗時の例→未決定を切り出す→方式の候補・影響・推奨を作る。複雑な関係だけ図を使う。
- **判断境界**：MVP、処理先、保持、共有、費用・精度の妥協は独断確定しない。既存の決定は再質問しない。仕様案の作成と採用を区別する。
- **検証・完了**：各振る舞いに根拠、期待結果、未決定が対応し、依存する判断が分かる。矛盾があるなら「設計案完成／採用待ち」と報告する。
- **記録先**：短い決定は正本の該当項目とWORKFLOW（更新が許可された時だけ）。詳細仕様は許可された場所へ分離し正本から参照。正本の変更は現在の依頼に含まれる場合に限る。

仕様記述の最小例（架空の設計様式であり新規仕様ではない）：

```text
振る舞い／根拠D・S:
入力・利用者・事前状態:
期待する結果／起こしてはいけない結果:
境界・失敗ケース:
未決定O／必要な判断:
確認方法／採否・決定理由・日付:
```

### 3. 実装

- **入力・参照**：明示された実装依頼、採用済み仕様、変更範囲、完了条件。製品正本、該当実装、既存テスト、開発先の指示を確認。
- **道具・手順**：既存コード・実行設定を読む→差分と影響を整理→必要な確認を決める→最小の一貫した変更→起動・対象確認→失敗を直し影響範囲を再確認。編集は差分で行い、他者の変更を消さない。
- **判断境界**：本書は実装許可ではない。未採用仕様や許可外の導入・公開に依存する場合は該当部分だけ保留。作業に必要な実装上の判断は現在の依頼・上位指示が許す範囲で行う。
- **検証・完了**：確定した振る舞いが確認でき、変更に必要な既存チェックが成功し、未実施を明示できること。固定された不具合契約には、可能なら失敗再現→修正→成功確認を使う。小さな表記修正へ不要なテスト追加を強制しない。
- **記録先**：開発先の仕様・テストとWORKFLOWへの要約。コマンドは実際のmanifest・README・スクリプトから確認して記録。未決定技術の架空コマンドは書かない。

### 4. 不具合修正

- **入力・参照**：期待と実際の違い、再現条件、対象版、個人情報を除いたエラー。仕様、実コード経路、関係するログ・テスト。
- **道具・手順**：再現→原因候補→該当コード・状態を追跡→最小修正→同じ条件と隣接ケースを再確認。UI症状だけからAPIやモデルの原因を断定しない。
- **判断境界**：期待動作が未決定なら仕様相談へ戻す。依存環境の失敗と製品の不具合を分ける。修正のために精度・共有条件を黙って変えない。
- **検証・完了**：元の失敗が解消した直接の証拠と、影響範囲の確認がある。再現不能なら原因仮説として報告し、修正成功としない。
- **記録先**：WORKFLOWに症状→原因→修正→確認の対応。詳細ログは許可された安全な場所を参照。

### 5. 検証・技術比較

- **入力・参照**：検証する仮説または確定仕様、対象版・条件・比較対象。製品のケースはVALIDATIONの必要項目だけ選ぶ。
- **道具・手順**：正解・観測単位・失敗の扱いを定義→データと実行範囲の許可を確認→適切なテスト／ブラウザ／状態・ログの観測→結果と比較・限界を記録。
- **判断境界**：探索で数値を得ることと合否判定を分ける。O10未決定なら合格値を創作しない。音声実験は別途条件が必要で、自動再開しない。
- **検証・完了**：比較条件の差、件数・分母・集計方法、未判定・失敗を含めて解釈できる。共有の正しさと認識・統合精度は別に測る。
- **記録先**：製品比較の詳細はVALIDATIONの様式、経過と次の判断はWORKFLOW。人工信号・架空例・実測を明示する。

| 変更・問い | 選ぶ確認方法 | 限界・省略するもの |
|---|---|---|
| 表記・リンク | 差分とリンク先、必要なら表示 | 無関係な全体テストを繰り返さない |
| 確定した計算・変換 | 既知入力と期待出力、境界・失敗 | 実装の内部構造をなぞるだけのテストは避ける |
| UIの利用体験 | 実ブラウザで操作・画面・状態 | ビルド成功だけで画面正常とはしない |
| 共有区間 | 閲覧者と時刻境界、原記録と派生出力を比較 | 話者認識の成功だけで共有正常とはしない |
| 性能改善 | 同条件の改善前後・失敗と悪化も計測 | 1件の成功で一般化しない |
| 文書・AI指示 | 現実的な依頼で参照経路と判断を照合 | 文書レビューで実モデルの遵守を保証しない |

### 6. レビュー・改善

- **入力・参照**：ユーザー原要求、完成した変更の範囲、正本・制約、対象版またはファイル指紋、確認結果。
- **道具・手順**：先に単独で差分と完了条件を確認。独立レビューが依頼・許可された場合だけ、新しい文脈へ必要資料を渡す。具体的な問題を検証し修正する。指摘件数を成果にしない。
- **判断境界**：通常の小タスクで自動委任しない。レビューの回数・モデル指定は現在の依頼に従う。過去Goalの条件は継承しない。将来の重要変更では独立レビューの必要性を提案できるが、本書から起動権限を推定しない。
- **検証・完了**：読まれた内容と最終内容が対応する。意味や境界を変えた場合は必要な再確認を行い、未解決を残したまま承認扱いにしない。
- **記録先**：WORKFLOW／今回の基盤確認記録。自己レビューと独立レビューの別、対象、結論、修正、残件を残す。

### 7. 報告・引き継ぎ・再開

- **入力・参照**：今回の目的、変更、実行結果、判断、残件。WORKFLOWと現在の引き継ぎ。
- **道具・手順**：重複しない短い記録を保存→参照の存在と現在の状態を確認→成果・限界・次の判断を返す。圧縮前にも保存する。
- **判断境界**：人間の決定のない箇所は案のまま。次の作業案を実行許可としない。コンテクスト圧縮は利用可能な操作がある場合だけ。
- **検証・完了**：次のAIが目的、正本、許可範囲、未決定、次の判断へ辿れる。新しい会話で試していなければ、引き継ぎ成功の実証とはしない。
- **記録先**：WORKFLOWの短い作業記録と、[FOUNDATION_HANDOFF.md](../history/FOUNDATION_HANDOFF.md)の入口・現在地。

## MVP 2.0を二人で進めるとき

今回のKとM/U/受入ID、仕様・契約・fixtureの版を両担当で揃える。詳細な着手順と依存はロードマップ§7、各AIへの依頼例と引き継ぎ項目は開発開始ガイドに一本化する。旧音声探索の再開を前提にせず、未検証事項を該当Kで確認する。G1〜G5は製品内の処理役割であり、開発AIの委任許可ではない。

## 決定と資料を更新する

ユーザーの決定を受けたら、変更内容・理由・関係D/S/O・範囲・日付を特定する。依頼の変更先に正本が含まれる時に正本を更新し、関連する仕様・検証期待・人向け資料の必要箇所を照合する。許可外なら更新案と反映待ちを記録する。詳細は一か所を正本にし、他はリンクする。過去結果は削除せず対象版を明記し、現在の結果と区別する。

仕様・画面・採用技術が未決定の欄には「確定後記入／判断者／必要になる時点」を置く。新しい仕様書が必要になった時だけ作る。今回の基盤のために全機能の仕様書を空で量産しない。

## 別の開発ディレクトリへ適用する場合

1. ユーザーの指定した開発先の絶対パスを確認する。リポジトリ名からパスを推測しない。
2. 上位・開発先のAGENTSや既存変更を読み、取り込む範囲と正本の置き方を決める。適用先の編集許可が必要。
3. チームで参照可能な場所へ正本を置くか、明示的な外部参照を使うかを選ぶ。後者はそのマシン以外で存在を保証しない。無管理な二重正本を作らない。
4. 開発先のAGENTSを上書きせず必要な入口を統合し、相対リンクの解決と指示の衝突を確認する。調査資料や個人パス、私的資料を無断公開しない。
5. 新しい会話で小さな読み取り依頼を試し、参照先・判断境界を説明できるか確かめる。導入と実利用確認を別に記録する。

共有版ではルートAGENTSと資料入口を配置しています。受け手の環境での参照・起動は未確認です。資料の配置を製品開発環境の完成とは扱いません。
