# 最初の音声検証：2台の記録に補完の余地があるか

状態: 実行手順とユーザー報告の検証ケースを記録。テーブル／ポケットの2パターンについてユーザーから収録内容の説明あり。音声ファイルの確認・採点・評価は未実施。MVP・方式採用ではない。

## 最新の検証ケース：テーブルとポケット

以下はユーザーが説明した検証内容の記録。AIが音声を聴取して確認した事実や転記ではない。**次のセッションではまずこの2ケースを扱う。** 後述のR01〜R03は従来の追加検証案として保持し、今回のケースをその3組へ自動的に数えたり、先に録り直しを求めたりしない。

ユーザー訂正により、Aさん側=iPhone 16／ボイスメモ、Bさん側=Google Pixel 8（Android）／レコーダーと確定。端末A/Bの表記もこの対応へ統一する。評価記録では `TABLE-A側` 等のケースIDを使い、実ファイルとの対応だけを人が記録する。

### POCKET-01：AさんのiPhoneはポケット、BさんのAndroidは机上

- 配置：AさんのみiPhoneをポケットに入れる。BさんのAndroidは机の上のBさんの手元に置く。「双方がポケット」という以前の記載はユーザーの訂正により撤回。
- 会話：用意したお昼のスクリプトに沿った内容。ラーメンの提案、暑いのでそばという別案、そばに決定、店は未決定という架空例を参照する。
- 確認：各録音で案・理由・決定／未決定・発言者の根拠を聞き取れるか。衣服による遮蔽や擦れがあれば、その区間と聴取への影響を人が記録する。両方を聞くことで回復・悪化した項目を分ける。
- 未確認：ポケットの位置・端末の向き、開始／終了の順序と秒位置、録音時間、実発言との差分。テーブル版と同じ開始／停止順とは仮定しない。

### TABLE-01：テーブル上で録音区間をずらして会話

| 順序 | Aさん側の録音 | Bさん側の録音 | ユーザー説明による内容 | 確認する点 |
|---|---|---|---|---|
| T0：Aさん側の録音を開始・再開 | ON | OFF | Aさんの趣味であるサッカーの話 | Aさん側だけに収録される冒頭区間として区別できるか |

T0〜T3は順序のラベルで、測定済みの時刻ではない。「開始・再開」が新規録音か一時停止からの再開か、ファイルが分かれるかは未確認。録音内の秒位置は人が実ファイルから記録する。「3時」はユーザー説明どおり保持し、日付や15時への変換を音声根拠なしで補わない。

### この2ケースから確認することと限界

1. **内容の所在**：サッカーはTABLEのAさん側のみ、お昼の共通部分は両方、3時の決定はBさん側のみという説明を実録音と照合する。相手側に存在しない区間は「未収録」とし、同じ区間を録ったのに聞き取れない場合と分ける。
2. **部分重複**：TABLEのT1〜T2に共通部分があるか、その対応点と前後の単独部分を人が確認する。自動時間対応の実行は別途手順・正解時刻を用意してから行い、今回の説明だけでV01/V03成功とはしない。
3. **補完の種類**：共通区間の聞き取り改善と、片側だけ録音していた区間を両方の確認で読めるようになることを別集計する。後者を複数マイクによる音質改善とは呼ばない。
4. **配置**：Aさんのポケット内iPhoneとBさんの机上Androidの収音状態を観測する。端末・話者との距離も異なるため、同じケース内のA/B差をポケットの影響だけと判断しない。ただし会話内容・長さ・開始停止が揃っていないため、2ケースの差を配置だけの効果とは断定しない。厳密な配置比較は必要と判断した場合に条件を揃えて追加する。
5. **録音と共有の分離**：BさんがT1で録音開始したことは、その時点で初めて会話へ参加した証拠ではない。AさんもT2以降の会話には参加している。物理的参加・録音範囲・製品の閲覧権限は別に扱う。両方の録音を人が実験で確認できても、Bさんへの冒頭共有やAさんへの「3時」の自動共有を許可する製品判断にはしない。

今回のスクリプトと期待内容は既知のため、動作・区間・採点手順の探索材料として扱い、未知の会話に対する精度や補完の一般的優位性の証拠にはしない。§6の記録表へケースID・共通区間/片側のみ・未収録の区別を追加して使う。採点と正解確認は人が行い、AIへは匿名集計だけを返す。現行の利用・保管条件は維持する。

## 1. 今、何の判断をするか

目指す体験は「日常の会話で出た案と背景を、後から取り戻して続きを話せる」。今回の問いは **各端末単独では不明・誤りになる案、理由、発言者などが、人が両方の録音を使うと回復するか**。

自動処理に工数をかける前に、入力そのものに補完材料があるかを調べる。技術検証を今行う理由は複数端末統合という核の不確実性を下げるため。共有UIの理解確認が済んだことは、録音の価値や継続利用の実証ではない。

| 今回測ること | 今回は測らないこと |
|---|---|
| 2端末の録音を保存・取り出し・人が再生できるか（P0/A01） | 自作アプリの録音継続・電池消費 |
| 各単独と、人が両方を確認した回答の回復・悪化（P1/A03、A09の問いを借用） | 自動文字起こし・自動統合の精度 |
| 答えの根拠となる発言を録音内で示せるか | 声からの本人認証・端末所有者の識別 |
| この場面で残したい内容、準備と確認の負担への反応 | 別会話の誤結合率、共有権限の安全性、文化の定着 |

P1はV04に関する「人による補完余地」の探索であり、V04全体の合格ではない。時刻差候補だけを求める既存コードは今回は使用しない。WAV変換も人が元ファイルを再生できるなら不要。

## 2. 最小の実施量と配置

以下のR01〜R03は、既存2ケースの探索後に追加が必要と判断した場合の手順。今回のTABLE／POCKETへ同条件3組という条件を遡って要求しない。

- 端末A: iPhone 16／ボイスメモ（Aさん側）。端末B: Google Pixel 8／レコーダー（Bさん側）。ユーザー訂正に合わせて統一済み。
- 人物はP・Qと呼び、端末A/Bと区別する。2人とも内容を知る評価なので、記憶の影響を排除した試験ではない。
- 最初は静かな室内、2人がテーブルを挟んで座り、各端末を各自の近くへ置く。距離・向き・配置をメモする。イヤホンや外部マイクは使わない。音量を不自然に落としたり、端末を覆ったりして差を作らない。
- **同じ配置条件で、異なる内容を3組。各60〜120秒、2台分で計6ファイル。** 1組目で保存と評価方法が成立しなければ、残りは録らず不足を直す。
- R01/R02は手順の調整用、R03は未使用の確認用。R03を聞く前に評価手順を固定する。途中で手順・配置を変えた場合は別条件と記録し、3組を同条件の反復と集計しない。R03を調整に使ったら未使用扱いを解除する。
- 録音開始はA→Bの順でよい。両方の開始を確認してから会話を始める。意図的な開始差・部分重複は今回は設けない。今回の目的に不要な変数を増やさない。

所要時間は準備と評価速度による。録音自体は計3〜6分だが、正解確認・比較には別途時間が必要。全体所要時間は初回に実測する。

## 3. 録音前に人が確認すること

現行条件を変更しない。参加する2人の具体的な了承、評価で両方の録音を聞くこと、保管先・閲覧者を人同士で確認する。実験の両録音閲覧は製品の自動共有許可とは別。

端末・転送先ともクラウド同期外、PCはリポジトリ外の保存先とする。レコーダーのバックアップ・ボイスメモのiCloud同期・転送先の同期状態を確認する。設定操作で既存の個人録音を削除しない。転送経路が確保できない場合はP0未完了で止める。

実音声・転記・正解文・特徴量はCodexに送らず、人がPC内で扱う。実験終了後7日以内の削除条件は原本・派生物にも適用する。今回AIは実録音を再生・変換・解析しない。

## 4. 会話と質問を先に決める

### 追加：まず簡単な会話で準備を確認する

ユーザーの「会話を簡単にしたい」という希望への提案として、練習ID **PRACTICE-01** を設ける。次の文はAIが作った架空例であり、実録音の転記ではない。

> P「お昼、ラーメンにしない？」
> Q「今日は暑いから、そばがいいな」
> P「じゃあ、そばにしよう」
> Q「どのお店にする？」
> P「お店はまだ決めてない」

この短い練習では録音・保存・転送・再生と、根拠時刻を評価表へ記入できることだけを確認する。期待する内容は最初の案=ラーメン、別案=そば、理由=暑い、決定=そば、未決定=店、別案の提案者=Q。実際に言い換えた場合は実発言に従う。練習の質問はこの6点とし、本検証のQ1〜Q6へ無理に対応させない。

**答えを事前に示した短い台本なので、補完効果・精度の証拠にはしない。R01〜R03の3組にも数えない。** 60秒へ引き延ばす必要はなく、時間差コードの入力にも使わない。準備を既に確認できていれば練習は省略可能。録音前の了承・同期外保管は§3どおり必要。

### 本検証の会話

R01は「次の休みに友人と遊びに行く相談」を使用する。R02は「持ち寄りの食事」、R03は「一緒に試したい趣味」など別内容にする。これらは実験用の架空場面であり、製品の対象を旅行や予定管理へ限定するものではない。

自然なやり取りの中に、案・理由・別案・まだ決めていない点を含める。文言を読み上げる固定台本にはせず、実際に言ったことを評価する。話した内容の全てを決定事項やTodoにしない。

各組について、録音前に次の共通質問を評価シートへ用意する。

| 項目ID | 振り返りの質問 | 評価単位 |
|---|---|---|
| Q1 | 最初に出た案は何か | 案の内容 |
| Q2 | その案の理由は何か | 理由の内容 |
| Q3 | 別の案・変更案は何か | 別案の内容 |
| Q4 | 別案・変更案の理由は何か | 理由の内容 |
| Q5 | 最初の案を出したのはP/Qのどちらか | 発言者 |
| Q6 | 最後に何が決まり、何が未決定だったか | 決定状態 |

Q6で独立した複数の事実を採点する場合、正解表でQ6a/Q6bと分割してから全条件を同じ単位で採点する。必要な発言が実際にはなければ、想定台本から補わず「発言なし」を正解にできるか人が確認する。記録不足で不在を確認できない場合は正解不明に分ける。

### 採点規則（全条件共通）

正解作成では、必須の意味要素・発言者・決定状態・根拠区間を定める。単独/両方の回答を採点する前に正解表と項目の分割を固定する。正解作成時は回答欄を閉じて録音を照合するが、同じ2人のため記憶による影響は残る。採点後に都合よく分割・正解を変えない。訂正が必要なら理由と版を残し、全条件を再採点する。

- **正答**: 必須の意味要素を満たし、矛盾・事実として述べた創作を含まない。同じ意味の言い換えは許容する。
- **誤答**: 必須要素の一部が欠けた部分正答、内容・人物・決定状態の誤り、正しい内容に創作を付け足した回答。部分点は付けない。誤りと明示的な不明が混在しても誤答を優先する。
- **不明**: 誤った断定をせず、回答全体または不足要素を明示して判断を留保した回答。正答率の分母Nには含める。
- **正解不明**: 録音の根拠が不足、または正解について2人が一致しない。Nから除き件数を別記する。単なる無回答とは区別する。
- **根拠**: 指定区間内に回答を支持する発言があり、その端末を正しく参照していれば一致。無関係・矛盾する発言なら不一致、指定なし・聴取不能なら不明。回答の正誤と別に数える。話者と端末所有者を同一視しない。

## 5. 人による実施手順

1. **R01を録音・保存する。** 原本を編集せず、R01-A／R01-Bという対応を記録する。拡張子、録音秒数、配置、保存・転送・再生の成功/失敗だけを確認。内容を精査する再生は次の評価と兼ね、事前に両方を聞き込まない。再生できなければP0で停止。
2. **単独で回答する。** PはAだけ、QはBだけを聞き、Q1〜Q6へ回答。分からない場合は不明と書く。回答ごとに、その端末の録音内の根拠時刻を記録する。相手の回答や音声、アプリの自動文字起こしは見ない。
3. **単独回答を保存して固定する。** 後から修正せず、次の回答を別欄へ書く。
4. **それぞれが両方で回答する。** PはBを追加、QはAを追加で聞き、自分の単独回答から何を変更したかを記録する。まだ互いの回答は見ない。両方を使う回答も一つに合議せず、P-AB／Q-ABとして独立に残す。
5. **最後に正解を照合する。** 2人で実際の録音を確認し、各項目の正解と根拠区間を作る。発言時の記憶だけで正解にしない。合意できない、両方とも聞き取れない箇所は正解不明。両音声にない内容を思い出しても回復成功には数えない。
6. **同じ正解表で採点する。** 単独・両方それぞれの正答/誤答/不明と根拠を採点。正解不明の項目を正答率の分母から除外し、件数は別に残す。
7. **R01で記録表が埋まることを確認し、R02/R03へ進む。** R02はPがB単独→両方、QがA単独→両方の順へ交代。R03はR01と同じ順。結果を見て良い端末・評価者だけを採用しない。

両方を聞く条件は情報量だけでなく再聴取時間も増える。評価者は録音参加者でもあり、再聴取・記憶・評価者差を分離できない探索である。改善があれば「追加した端末のどの音声を根拠に修正できたか」を確認するが、これだけで一般的な複数端末の優位性を確定しない。中央1台や自動処理との比較にもならない。

単独評価中に他方の再生音が聞こえないよう、評価は別室または再生用イヤホンで行う（録音時の外部マイク不使用とは別）。両方条件では追加端末を先に聞き、必要な根拠確認の再生回数と時間も記録する。聴取量を統制した優位性試験ではないことは維持する。

## 7. 終了条件と次の行動

**今回のTABLE-01／POCKET-01の終了条件**：各ケースで入力状態、区間ごとの収録有無、確認できた内容と根拠、聞き取れない項目、未確認事項が記録され、次の判断が一つ選べること。取得済みの音声を使った探索として完了可能。追加3組や全自動処理の成功は要求しない。後述の3組の終了条件はR01〜R03を実施すると判断した場合に限る。

終了は合格率ではなく、選んだ3組の状態・比較・根拠・限界・次の判断が揃うこと。入力や正解を作れなければ途中終了し、その不足だけを直す。数値の製品合格値は未設定で、1項目の回復だけをMVP採用条件にしない。

| 結果 | 次にすること |
|---|---|
| 追加した録音を根拠に回復できる項目がある | 回復対象を記録し、P2/A04（V01/V03）の時間対応とA05（V02）の負例を含む自動判定の計画へ。自動化可能とはまだ判断しない |
| 内容は同じでも発言者・根拠が改善 | A07/A09へ絞って確認。人が知人の声を覚えている効果を自動本人識別の証拠にしない |
| 両単独で十分、差がない | 差なしを記録。SC04で実際に想定する距離・移動等を1条件だけ追加する必要性を判断。架空の劣化で優位性を演出しない |
| 両方でも不足 | 収音・配置の問題か、そもそも発言なしなのかを分離。条件変更の提案へ戻る |
| 悪化・誤った根拠・創作がある | 改善件数で相殺せず個別に残す。原因を説明できなければ正解作成・評価手順を見直す |
| 正解不明・入力不備 | 判断不能。処理方式の成功/失敗とは別にP0・評価手順へ戻る |

次段階の時間対応検証では開始差・正解時刻・部分重複、同一会話と似た別会話の組を別途定義する。今回の録音だけでV01〜V04や安全な自動共有の成立を宣言しない。需要・日常の負担も並行して確認し、MVPは価値と技術の結果を合わせて人が決める。
