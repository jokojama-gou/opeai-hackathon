## 1. 開始時に揃えるもの

[AGENTS](../../../AGENTS.md)と[WORKFLOW](../WORKFLOW.md)で今回の依頼と現在地を確認する。製品方針は[PRODUCT_CORE](../../product/PRODUCT_CORE.md)、機能・画面・API・受入条件はMVP_SPEC、担当と接続順は[ロードマップ§7](../MULTIPLATFORM_DELIVERY_PLAN.md#7-macwindowsの開発ロードマップ)、日々の進め方は[開発手順](../DEVELOPMENT_PLAYBOOK.md)を参照する。

関連D01〜D17/S01〜S05、O01/O03/O04/O05/O07/O09/O10。O02の担当・提出方針は決定済み。旧Q1〜Q3やT01〜T09を最新仕様の代わりに使わない。既存の音声探索は一区切りであり、追加録音・全文採点・既存録音再評価・認識環境再構築へ戻らない。未検証は仕様書§12と対応するKへ引き継ぐ。

開始時は仕様版、採用範囲、今回のK、変更先、完了条件を揃える。A採用後のK01/K02、B採用後の方式実装、実データ・外部API接続前の条件を区別する。既に得た判断は取り直さず、独立した文書・契約設計は進められる。

## 2. 二人の担当

| 担当 | 主に進めるもの | 相手へ渡すもの |
|---|---|---|
| Go君 / Windows | React Native（Android/iPhone）、共通デザイン、API・認証・DB・認可、WindowsでのASR worker接続、契約の取りまとめ | schema/fixture/期待結果、APIとjob状態、RNビルド、受入結果 |
| あなた / Mac | SwiftUI、共通workerの個別ASR・統合・生成・clip処理、RN/SwiftのiPhone確認・配布 | Swift decode/画面結果、worker入出力と結果、iPhoneでの差異・失敗 |
| 各人のAI | 担当範囲の設計・変更・検証・記録 | 対象版、差分、証拠、未達、次の確認 |

処理コードの担当と実行場所を分ける。仕様書§9の提案ではWindows側の共通API/ASRへ接続し、MacへASR環境を重複構築しない。K03はあなたがASR adapter・正規化・Source生成のコード版/起動条件を渡し、Go君がWindowsでAPI/jobと接続した結果を返す。人工状態と実ASRの確認を分け、実音声経路は必要な実行条件が成立してから扱う。共有ファイル・依存設定・DB定義・WORKFLOWは、その作業で一人を編集担当にする。固定の役職や全作業への二重承認は増やさない。

## 3. 着手順と完成の区切り

チケットの定義元はMVP_SPEC §11。番号順ではなく依存関係で進める。

| 順序 | 作業 | 二人で確かめる結果 |
|---|---|---|
| K01 → K02 | 同じ人工契約から「記録→会話詳細→根拠」を両画面へ | duplicate/conflict/pending/expiredの4fixtureをTS/Swiftが同じように受理・拒否し、期待表示に一致 |
| K03 / K04 | 個人記録の保存・送信・個別ASRと、持ち寄り・本人/参加確認・双方許可 | K03は入力metadata→job→Source/ASR状態まで確認し、保存・送信・文字起こしの成否を分離。未回答・不一致は共有せず、取消と継続解除を区別 |
| K05 → K06 | 2入力の統合とG1整理、原音・訂正・指摘・再生成 | 出典・相違・不明を保持し、旧版や権限外の本文を公開しない |
| K09 | 今日・ToDo・保存/メモ・確認一覧 | K01/K04を土台に人工出力でAPIまで確認。UIはK02から並行可能 |
| K10 → K08 | 共通runnerと日次、G3の予定抽出からカレンダー登録 | G2/G3/G5を実生成へ接続し、G4はコード処理。目的別許可・失効・二重作成・再試行上限 |
| K07 | 2.0全体の通し確認と提出版選択 | AC01〜AC19、C01〜C09、A01〜A15の計43条件と両クライアントの証拠 |

K08の人工画面はK09と並行できるが、実登録はK05/K10のG3実生成と必要条件の成立後。M01〜M08だけで2.0完成とはしない。3主タブ「今日・記録・保存」、M01〜M14/U01〜U15は仕様書§2〜4、追加機能は§14/§15を参照する。

グループ実画面、3人以上の実共有、自動発見、全文/意味検索、同じ録音への一時停止・再開は後続。通常/グループの確定した権限方針と契約ケースは保持する。

## 4. 一つの作業を進めるサイクル

1. 今回のK、関連M/U/受入ID、対象版、変更先、依存する判断と完了条件を短く記録する。
2. Go君が契約を取りまとめ、あなたがSwift/workerの要求を返す。同じfixture、エラー、版、失効時の期待結果を先に合わせる。
3. 両PCの別checkout/作業ブランチで担当範囲を変更する。未コミット差分は相手のpullには含まれないため、受け渡す版とファイルを明示する。
4. 固定した契約は失敗再現→実装→成功確認。画面・API・workerを接続し、単体成功を通し操作の成功に置き換えない。
5. 原要求と差分を自己レビューし、相手は同じfixture/ビルドで結果を返す。独立AIレビューは依頼された場合に使う。
6. WORKFLOWに結果・証拠・未達・次の受け渡しを残す。仕様変更はMVP_SPECの該当箇所へ戻り、両アプリへ反映する。

必要なときだけ[GUIDE](GUIDE.md)からdesign/implement/review/handoffを選び、根拠不明の問いはresearchへ戻す。小さな修正に全skillを強制しない。

引き継ぎには「担当/K/仕様版と採用範囲」「M/U/受入ID」「対象コミットまたはファイル版と未コミット差分」「API/schema/fixture/manifest版」「端末/OS/ビルドと成功・失敗・未実行」「証拠」「相手への確認事項・残件」を残す。模擬・実生成・実音声・外部登録の結果を分け、受け手の証拠が揃うまで相手PCで確認済みとしない。

## 5. 接続時に落とさない確認

- ContextViewの個人/共有を二重採用しない。根拠は個人ならU03、共有ならU06/U07へ戻す。
- 取消・訂正・期限切れはToDo/保存/メモ/日次・件数・キャッシュ・生成入力にも反映する。§15.4のmanifest依存を両画面で確かめる。
- G1〜G5は製品内の役割であり、開発AIの委任とは別。G4はモデル呼出なし。runnerは§15.5の再試行・同時実行・予算上限に従う。
- ToDo採用/完了、保存/メモ、日次対象選択は本人操作。予定登録は§14の本人許可と最新条件をexecutorが再確認し、モデル出力だけで外部書込しない。
- K07では統合→相違確認→ToDo採用→保存/メモ→予定登録→別会話を含む日次→根拠を通す。決定や行動のない雑談も扱う。実処理未接続なら人工データの操作デモと報告する。

## 6. 各AIへ渡す最初の依頼例

準備・設計を頼む例。実装を依頼するときは採用範囲と今回のK・変更先を明記する。

**Go君 / Windows:** AGENTS、WORKFLOW、MVP_SPEC 2.0 §11、ロードマップ§7を読み、K01の契約とK02のRN画面の計画を具体化してください。担当はRN、共通デザイン、API/認証/DBです。Macへ渡す4fixture・schema・期待表示・エラー/版を整理し、§15との整合も確認してください。今回のK01へ全機能実装を詰め込まず、不足する採用判断と環境条件だけ示してください。今回は文書・設計まで。既存変更を保持し、音声探索・製品実装・導入・送信・commit/pushは開始しません。

**あなた / Mac:** 同じ資料を読み、K01のSwift適合確認とK02のSwiftUI画面の計画を具体化してください。Go君のデザイン・共通契約と同じ4fixtureを使い、未受領なら必要項目を渡せる形にしてください。K05/K10のworker入出力は共通契約への要求として整理し、別APIやMacのASR環境を作らないでください。iPhoneのRN/Swift確認に必要な環境・配布条件の不足を整理してください。今回は文書・設計まで。既存変更を保持し、音声探索・製品実装・導入・送信・commit/pushは開始しません。

今回の完了は開発資料の同期。各PCでの起動、相手への共有、製品受入条件の実行は別に記録する。
