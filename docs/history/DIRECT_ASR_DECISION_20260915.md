# 端末直接ASRの判断と移行計画

2026-09-15。対象版 `2d36ff616dc28471f40c00a04945659e8941b7bd`＋既存差分。ユーザーが各スマホから外部書き起こしAPIへの直接音声送信、必要時の端末側チャンク化、当日用APIキーの端末配布を指定。主担当AIが設計判断を反映。aidd-lite-designを継続適用。関連K01/K03/K05/K07、M01/M02/M04/M06、U02/U03/U07、AC01/02/05/07/14、O03。

## 決定と範囲

正本は[MVP_SPEC §9.0](../product/MVP_SPEC.md#contracts)。WindowsでASRを中継する必須経路を外し、録音・送信・必要な分割・応答正規化を端末へ寄せる。APIキーの端末配布は今回了承済みとして扱い、キー秘匿を理由に中継サーバーを要求しない。

共有記録の保存、統合、AI会話の配置まで選ばれたとは扱わない。製品の共有許可・参加範囲・根拠は機能として維持する。先行[調査](BACKEND_PLANNING_20260915.md)のWindows構成を第一候補とする案は、ASR経路について本決定で更新された。

## Windowsを全体から外す次の構成案（未採用）

- 各アプリ→ASR API→端末で結果をSourceへ変換。
- 両端末の結果→クラウドSupabaseへ保存・共有。
- 統合/AI会話→クラウド側の関数、または明示した片方の端末から生成APIを呼び結果を保存。クラウド側なら重複起動を集約しやすく、端末側なら処理を始めたアプリの終了・通信断を扱う必要がある。配置は別途決める。
- クラウドSupabaseは既存接続資料を再確認して利用先を確定する。既存ローカルSupabaseを使い続けるだけではWindows依存は消えない。

## 次の実装の順番

1. Go君のprovider/modelの採用結果とAPI仕様を受領。ネイティブとPWAを区別し、ファイル形式・サイズ・時刻・話者出力、PWAの場合はブラウザからの呼出可否を確認する。
2. 1台で録音→直接送信→原文表示。まず1ファイルで成立するか確認し、制限がある時にだけ分割を具体化する。現行useCapture.web.tsは録音を提供しないため、PWAならWeb録音自体も実装対象。
3. 端末でrecording_id/版、処理ID、各チャンクの元時刻・状態・結果を管理し、再送や遅着で重複/旧版復活が起きないことを人工入力で確認する。アプリ終了・復帰も扱う。
4. 2台のSourceを共通保存し、共有許可・時間対応・統合・根拠へ接続する。ASR前のPC音声uploadを必須にしない。原音を共有再生する保存経路は別に設計する。
5. M15の参照・履歴ルールを確定しAI会話を接続。両OSの実機で確認する。
