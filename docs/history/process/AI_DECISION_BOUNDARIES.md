# AIへ任せる判断と、人が決める判断

## 目的

AIが確定した目的の達成に必要な作業を自律的に進めながら、製品の意味が変わる未決定事項を推測で実装しないようにする。質問の数を増やすことではなく、判断の種類を分け、必要な判断だけ具体案とともに確認する。

## 推奨する境界

### A: 依頼範囲内でAIが判断して進め、結果を報告する

前提: 当該作業が既に依頼され、目的・完了条件・変更範囲が明確で、確定仕様や利用者との約束を変えないこと。計画の依頼から実装を開始する根拠にはならない。

- 既存資料の読解・比較、重複整理、参照修正。意味の変更や提案の採用は含めない。
- 確定仕様を満たす内部の関数分割、命名、モジュール構成、既存の仕組みを使う実装。
- 依頼された機能を成立させるための不具合修正と、仕様に対応するテスト・確認。
- 依頼範囲内の性能改善。ただし精度・共有範囲・保持・費用等の合意条件を変えない。
- 調査・試作を依頼された場合、その範囲内の比較資料、実験専用コード、結果の整理。試作の選択を製品への採用にしない。

内部変更でも、外部へのデータ送信・費用・権限・運用や既存データへ影響する場合はB/Cの判断を確認する。既に許可された同じ条件は再確認しない。

### B: AIが選択肢・影響・推奨を準備し、未決定の製品判断を人に確認する

- 誰の何を記録・統合し、誰にどの区間を共有するか（D04〜D12/D17、O04〜O09）。
- 曖昧な判定の確認先、未回答、意見の不一致、停止・訂正・削除・取消の意味。
- 音声や派生データの保持、外部処理、未導入者、グループと会社の閲覧権限。
- MVP、初期対象、機能の追加・除外、画面に持たせる役割、主要な操作やユーザー負担。
- 品質・速度・費用が両立しないとき、何をどこまで許容するか。
- 作業の目的や優先順位の変更、依頼に含まれない段階・範囲への拡張。

既にユーザーが明示した決定はそのまま反映する。方針変更を明示した依頼も二重承認にしない。矛盾の意図や変更範囲が不明なときだけ聞く。

### C: AIが調査・検証で判断材料を集め、製品への採否を人が決める

- 同一会話の照合、話者と端末の識別、複数端末補完の方式（D13/O04）。
- 対象端末・OS・Webかネイティブか、長時間録音・近距離通信の方式（O02/O06）。
- 処理場所、サービス、基盤構成の選択（D15/O03）。
- 性能の測定と、実現できる範囲を踏まえたMVPの選択（D14/O01/O10）。

検証の実行自体にも依頼範囲とデータ・費用等の条件が必要。未承認の実験を「判断材料を集めるため」として開始しない。実験限定の採用と製品採用を分ける。測定で分かる事実と、利用者として許容するかという判断は別に記録する。

## このプロダクトでの具体例

| 依頼・状況 | 区分と判断 | 理由 |
|---|---|---|
| 資料のリンク切れを修正して | A。修正と参照確認を進める | 既存方針を変えない文書整備 |
| 確定したCの参加前制限を実装して | 実装依頼の範囲内ならA。D09/D17を満たす方法とテストを選ぶ | Cの要約・検索・AI回答に含めず、A・Bの利用は維持する方針は確定 |
| Cにも参加前の話を要約だけ見せたい | 通常共有ではD17と不一致。変更意図が不明ならB。グループ利用ならO09の適用範囲を確認 | 通常共有とグループ共有を混同しない |
| 判定確認に返答がなければ、翌日に自動共有しよう | B。未回答時の仕様を選ぶ | 時間経過を同意とみなす動作は未決定（O05） |
| 停止ボタンを実装して | 停止対象が未決定ならB。その判断と独立した範囲内の作業は続ける | 本人録音・本人共有・会話全体の終了は異なる（O06） |
| 共通ノートの削除時、全員分も消すようにして | B。明示された依頼の範囲と既存方針を確認し、未決定の派生物・会社履歴の扱いを具体化 | 共同記録の権利・保持に影響する（O07/O09） |
| データ転送が楽なのでクラウド処理にしておく | B/C。処理場所を採用済みにしない | D15は未決定。実装上の都合だけで選ばない |
| 時刻差の推定方式を比較して | 比較が依頼され、入力・実行条件が揃えばCの検証作業を進める | 相関結果は参加者や共有権限の証明ではない |
| 二つの内部関数を共通化したい | 依頼範囲内で振る舞いを維持するならA | 新たな製品判断を伴わない |
| 振り返りには出来事一覧が良さそう | B。採用案として理由を提示 | 価値は確定しているが画面方式は未採用 |
| API費用を減らすため文字起こしの精度を下げる | 合意した品質条件を満たす内部改善ならA。新しい許容値が必要ならB/C | 技術変更という名前でも利用価値が変わる |
| 良い機能ができたので公開する | 現在の依頼が公開を含むか確認。含まなければ別の実行判断 | 資料や委任方針の採用だけで公開まで許可されない |

## 確認が必要なときの進め方

1. 既存資料と会話から、同じ判断が済んでいないか確認する。
2. 今回の作業がその判断に依存するかを特定する。依存しない未決定事項は、確認時点を残して後に回す。
3. 「決めること／今必要な理由／選択肢と影響／推奨と根拠／回答まで進められること」を短く示す。
4. 回答に依存する部分を待ち、独立した許可範囲の作業は進める。未回答を採用と扱わない。
5. 決定と理由を正本または判断記録へ反映し、関連資料を整合させる。回答を次の全作業への包括承認にしない。

## 依頼と完了報告の案

依頼を受けたAIは、目的・段階・変更範囲・完了条件を短く言い直す。不足をすべて質問するのではなく、今回必要な判断だけ特定する。

完了時は、成果、重要な判断と理由、確認したこと、未決定・未検証、次にすることを報告する。通常の内部判断を逐一承認に回さない。段階や目的が変わる場合は、次の成果物と範囲を具体化する。

## 採用と反映の計画

1. この境界案の採用または修正点をユーザーに確認する。
2. 採用後、AGENTSへ重複を増やさない形で反映し、HANDOFF_AUDITのU8を更新する。既存の個別承認条件は、明示的に変更された範囲だけ更新する。
3. U2〜U7などの残る仕様判断を、関連工程と依存する作業へ割り当てる。委任ルール採用だけでそれらの仕様を確定しない。
4. AI向け正本と人向け説明の最終整合・机上確認へ進む。

本案の完成条件: 代表的な依頼をA/B/Cに理由付きで分類でき、再確認不要の範囲と新しい判断が必要な範囲を説明できること。本案を採用するかは未決定。現在の作成完了は、将来のAIの動作検証を意味しない。
