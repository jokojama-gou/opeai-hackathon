## 原資料から整理できる利用シナリオ

以下は2026-09-10にDriveから取得した「luma入力事項」「アプリ案議事録（仮）」および後続のユーザー発言を基に整理したもの。Driveの最新更新は再取得していない。シナリオの掲載は、ハッカソンでの必須実装への採用を意味しない。

### SC01 作業中に口頭で交わした決め事・変更・ミスを後から振り返る [2Bへの応用シナリオ]

- 対象: 土木作業や映画撮影など、屋外で多くの人が協働する環境。職種をこの二つだけに限定する決定ではない。
- 場面の前提: 朝礼のように全員に向けて話す内容は共通に伝達し、会社でも記録できている。一方、作業開始後に個別の場所・相手との会話で変更、不具合、指示が発生する。
- 課題: 作業中に口頭で交わした決め事、変更、ミスについて記憶だけでは内容や経緯を取り戻しにくく、会社にも正確な履歴を残しにくい。
- 欲しい結果: 作業中のやり取りを各自の端末で記録・統合し、後から何を決めたか、何を間違えたか、その経緯を振り返れる。会社での記録保持もこの履歴の活用につながる。
- 現在の位置付け: 記録と事後の振り返りを現場にも応用できるという説明に使う。2026-09-12に今回の主軸をSC04へ更新。会社の保管・管理やリアルタイム連絡を今回の必須機能にしない。
- 未決定: 振り返る際の閲覧・検索方法、会社側の閲覧権限・記録管理者・保存先・保持期間。
- 共有の制約: 会社で保持するという目的を、全個人記録の収集許可と解釈しない。既定の職場用記録と通常記録の区別を維持する。
- 根拠の区分: 2026-09-11に初期検証として指定されたが、2026-09-12に2Bへの応用例へ位置付けを変更。朝礼との対比はこのシナリオの前提であり、現場一般の実証ではない。

### SC02 現場の会話を日常的な振り返りに使う

- 対象: 現場で指示や相談をする人・受ける人。
- 場面: 業務後などに、その日のやり取りを見返す。
- 課題: 原資料は、事故やハラスメント等が問題になった時だけ録音を調べることへの問題意識と、普段から見返せるようにしたい意図を記載している。
- 欲しい結果: 良い指示の出し方や伝わりにくかったやり取りを振り返るための記録を得る。
- 根拠の区分: 原資料の価値構想。事故防止効果や改善効果の実証はない。自動的な人物評価・ハラスメント判定の実装要件にはしない。管理者へ全個人記録を共有する根拠にも使わない。

### SC03 対面打ち合わせの話者と文脈を残す

- 対象: 原資料のチームメンバー。
- 場面: ハッカソンの3人の対面打ち合わせを、1人のGoogle Meetから記録した。
- 起きた問題: 議事録で全員の発言が同じ利用者として扱われ、誰の提案・話だったのかが分からなくなった。
- 欲しい結果: 発言者と内容の関係を保持し、後からAIに渡す際も会話の文脈を失わない。
- 根拠の区分: 原資料に明示されたチームの実体験。既存サービス全般についての比較結果ではない。
- 位置付け: 統合・話者の品質を検証する候補。これを最初の販売対象や主デモと決めたわけではない。

### SC04 日常の会話を気軽に残し、案・約束・思い出を振り返る [今回の2Cの主軸]

- 対象: 友人・サークル・ゼミ仲間など。
- 場面: 原資料には、飲食店で以前の飲み会の話が出た際、内容を思い出せなかった経験がある。
- 欲しい結果: 会話で生まれたアイデア、行きたい場所、次の予定などを取り戻し、次の会話や行動につなげる。具体的な初回のGoogle予定登録はMVP_SPEC §14に定義し、それ以外の外部連携は後続。
- 根拠の区分: 思い出せなかった出来事は実体験。予定・役割分担の自動整理などは原資料の利用構想。
- 位置付け: 2026-09-12のユーザー明示により、日常の記録文化を後押しする2Cを今回のハッカソンの主軸とする。友人との食事・雑談は具体例の候補であり、利用者層やデモをこの場面に限定する決定ではない。

## 今回の2C体験と価値検証 [具体案・未採用]

### 継続して集まるチームの会話を蓄積する [機能方針は了承済み・具体体験は案]

2026-09-12: ユーザーがグルーピングにより一定期間同じチームで集まる人を支援すると明示し、反映を了承。学生の制作チーム・企画を進める仲間・職場などに適用する。通常の日常利用にグループ作成を必須にはしない。

- 利用場面の案: 数週間一緒に活動するチームが複数回集まる。次の集まりで、前回の案・理由・懸念と今回の変更を振り返り、続きを始める。
- 体験の案: グループを選んでそのグループ用の記録を開始し、会話ごとの記録をグループの履歴から振り返る。複数回の会話は区別して保持し、似た話題や所属だけで同一会話として結合しない。
- 価値の仮説: 前回の背景を説明し直す負担を減らし、何を考え、何が変わり、何が未決定かをチームで取り戻せる。グループ横断検索・自動比較・タスク管理はこの方針だけで必須にしない。
- 確定した境界: 個人の通常記録は所属だけでグループへ流れない。グループ向けに明示開始した記録を対象とし、通常共有の初発言条件を一律転用しない（D12/S04）。
- 2026-09-12確定: 欠席した現メンバーは加入期間中の記録を閲覧可、途中加入者は加入後の区間から、グループ退出後は過去分を含めグループ経由の閲覧を停止（S04）。
- 未決定: 作成・招待、管理者の退出手順、再加入時の過去履歴、共有先変更等（O09）。3ケースの了承をこれらの採用へ広げない。
- 確認方法: 架空の2回の集まりを使い、前回の案と今回の変更を根拠付きでたどれるかを確認する。通常記録の混入は失敗。欠席・途中加入・退出はS04の期待結果で確認し、実行結果は未実行のまま区別する。

### 学生・仲間の雑談から企画や共同制作につなぐ [有力な初期検証候補]

2026-09-12: ユーザーの提起と了承を受け、SC04の具体候補として追加。学生や起業に対象を限定する決定ではなく、今回の主デモ・MVPの最終採用でもない。

- 場面: カフェなどで学生や仲間が話すうちに、作りたいものや企画のアイデアが生まれる。正式な会議として始めた会話とは限らない。
- 欲しい結果: 数日後に案だけでなく、発想のきっかけ、面白いと思った理由、懸念、別案を取り戻し、続きを話したり試したりできる。
- 架空の確認例: 雑談で「こんなアプリがあったら面白い」と案が出た。次に集まった時、何を作る案だったか、なぜ必要だと思ったか、何がまだ決まっていないかを確認する。実体験・実録音の転記ではない。
- 検証: 記憶・メモ・単独録音と比べて、次の会話や制作に役立つ情報を回復できるか。録音で自由に話しづらくならないか、複数人が記録する負担に見合うかも確かめる。未決定の案を担当・期限のある約束へ変えない。
- 範囲: 日常の会話を次へつなぐ2Cの場面として扱う。プロジェクト管理、事業計画生成、企業向け管理機能を必須にしない。

### 記録から振り返りまでの共通体験案

**体験案:** 会話を残したいと思ったときに本人が記録を始め、各自の記録を合わせ、後からアイデア・約束・思い出とその背景を振り返る。記録を始めるときの相手への伝わり方、共有範囲への理解、終了時の操作も体験として検討する。自動録音や固定グループ加入を前提にしない（D01/D04/O08）。

架空例C: 友人との食事で「次の休みに海へ行きたい」と話し、後から「移動を短くして湖もよさそう」と盛り上がる。日程や行き先はまだ決めていない。翌日、何を話したか・なぜ興味を持ったかを見返し、会話の続きを考える。実体験・実録音の転記ではない。

- 記録開始: 残したいと思うきっかけがあるか、本人と相手が記録・共有を理解できるか、操作が会話の負担にならないかを観察する。初回UIはMVP_SPEC、実利用の告知条件は対象場面で確認する。
- 振り返り: 話した案・約束・思い出の背景を見つけられるか、残してよかったと感じる箇所と不要な箇所を確かめる。提案を確定した予定に変えず、記録にない理由を補わない。
- 再利用: 続きを話す・考える助けになるか、別の日にも使いたい理由や使わない理由を聞く。再利用意向と実際の継続利用を分け、文化が定着したという証明にしない。
- 技術: 同じ記録で各端末単独と統合を比較し、回復・欠落・悪化・根拠の違いを確認する。V01〜V04の成功だけで日常利用の価値を証明しない。
- 境界: 通常共有の途中参加はS02/D09/D17を維持し、参加前の内容を要約・検索・AI回答にも含めない。固定グループや会社への共有を日常利用の前提にしない。

最初のデモ候補は「自分で記録を始める→複数記録を合わせる→会話を振り返り、続きを考える」。一覧・検索・質問・音声再生の選択、合格値、対象端末、保持方針は検証後に判断する。リアルタイム通知・外部予定登録・会社管理をこの候補の必須機能にはしない。

## 2Bへの応用例と体験 [提案・未承認、今回の主デモではない]

以下は検討用の架空の会話。現場の実体験や標準手順ではない。ユーザー指定の場面から体験を提案するもので、機能や技術方式を確定しない。

### 例A: 土木現場で、途中で変わった段取りを確認する

- 10時、A「午後は東側の資材を先に片付けよう」。B「搬入のため？」。A「そう、午後の搬入前に場所を空けたい」。
- 11時、A「搬入が明日に変わったので、さっきの片付けは明日の朝にしよう」。B「分かった」。
- 後からの問い: 「東側の片付けは、結局いつに変えた？ なぜ？」。
- 欲しい結果: この記録内では最後に「明日の朝」と決めたこと、搬入予定の変更が理由だったこと、最初の指示からの変更経緯を確認できる。
- 要件候補: 同じ対象への複数の会話を時系列でたどれる。古い指示だけを返さず、変更の根拠へ戻れる。記録後の現実の最新状況まで保証しない。

### 例B: 映画撮影で、ミスと対応の経緯を振り返る

- 撮影中、B「今のテイク、背景に機材が映っていた」。A「機材を移動して、もう一度撮ろう」。
- その後、B「機材を移動して撮り直した」。
- 作業後の問い: 「なぜ撮り直したのか。何を直して、どこまで対応したと話していたか」。
- 欲しい結果: 映り込みの報告、移動して撮り直す決定、撮り直したという報告を区別して確認できる。
- 要件候補: 問題の報告、対応の決定、実施したという報告を混同しない。最後の報告が録れていなければ、対応完了を推測しない。音声だけから映り込みの事実やミスの責任者を独自に判定しない。

### 共通の利用体験の案

1. 各自が勤務の開始時に職場用の記録を始め、やり取りを残す。
2. 同一会話の記録を統合する。一方で欠けた発言が他方にある場合の補完を検証する。両方で欠けた情報を創作しない。
3. 後から、その日の「決めたこと・変更・問題と対応」を一覧で振り返る。
4. 項目を選び、誰が、いつ、何を話し、どう変わったかを確認する。特定の疑問がある場合の言葉による検索・質問も候補とする。
5. 整理結果から元の発言と前後の会話へ戻って確かめる。音声再生を含めるかは音声保持方針と併せて決める。

一覧を提案する理由: 忘れた出来事は、質問自体を思いつけない場合があるため。質問だけに依存せず、その日を見返す入口を設ける。これは検証する利用仮説。

この例から必要になるのは、記録、同一会話の統合、出来事の整理、時系列と根拠の確認。リアルタイム通知、外部のタスク登録、人物評価は成立条件に含めない。会社での保持は、権限を持つ人が後からこの履歴を確認できる方向で検討し、詳細な権限は別途決める。

### 検証方法の案

- 上記のような会話をチームで再現し、複数端末で記録する。実際に発言された内容と順序を評価用の正解として別に残す。
- 一覧から変更・問題に気づけるか、上記の問いに根拠付きで答えを見つけられるかを観察する。
- 古い指示だけを提示する、決定を完了扱いする、述べられていない理由を作る、別会話を混ぜる場合は失敗として扱う案とする。
- 一台だけの記録と統合記録で同じ問いを確認し、複数端末による改善を別に評価する。改善しなかった場合も記録する。
- 再現試験で確認できるのは、この例での成立性。実際の屋外環境での録音品質や利用価値の実証は別に必要。
- 所要時間、正答、根拠の一致、操作負担を観察する。数値の合格値や試験規模は未決定。

## 成功条件のたたき台 [資料から導いた提案・未承認]

| 評価する価値 | 観察したい結果 | まだ決まっていないこと |
|---|---|---|
| 内容を取り戻せる | 既知の会話について、求める発言・指示内容を記録から確認できる | 確認方法、所要時間、合格値 |
| 決め事やミスを振り返れる | 会話で述べられた決定、変更、ミスの内容と経緯を後から確認できる。会話にない原因を補って断定しない | 振り返りの操作、根拠の提示方法、合格値 |
| 気軽に記録できる | 日常の会話で本人が記録を始め、相手と記録・共有の理解を合わせられる | 開始・終了UI、参加意思の扱い、操作負担の評価 |
| 残してよかったと思える | アイデア・約束・思い出を背景とともに振り返り、次の会話や行動に生かせる | 閲覧体験、価値の評価、再利用意向と継続利用の区別 |
| 会社に履歴が残る（2B応用） | 作業中の変更・不具合・指示とその経緯を会社側で確認できる | 今回の必須条件ではない。権限、保存先、保持期間、評価方法 |
| 話者と背景が残る | 誰の発言かと、その前後の理由を取り違えず確認できる | 正解データと評価単位 |
| 複数端末が役立つ | 一台の記録と比較して、補完できた箇所と改善しない箇所が分かる | 比較方式、端末、録音条件 |
| 共有範囲が正しい | 通常共有では非参加者や参加前の内容を共有しない。職場用は明示された共有範囲に従う | 職場用の共有対象・権限と判定方式 |
| AIへ文脈を渡せる | 会話記録を根拠に、発言者や経緯を保持して後続の問いを扱える | アプリ内質問か外部への出力か、今回の対象か |

数値目標・全シナリオの実装・上記の評価方式は確定していない。資料由来の価値を測るための提案として記録する。

## 次に確認する判断

現在の実装入口は[ロードマップ](../development/MULTIPLATFORM_DELIVERY_PLAN.md#tasks)。2CとMVP採用済み範囲を再質問せず、後続の価値検証は現依頼の目的に合わせて選ぶ。

SC04の具体例から、記録開始・振り返り・再利用を確かめる場面と評価方法を具体化する。SC03は技術検証候補、SC01/SC02は2Bへの応用例として必要時に参照する。

前版のQ01〜Q02で求めた場面と価値は、まず原資料を基に整理する。新しい実体験の説明をユーザーに必須要求しない。

## 回答後に決める項目

- 会話の人数、端末の持ち方、距離・移動・騒音、記録の長さ。
- この場面で複数端末が解決すべき欠落・話者混同等の問題。
- 通常の会話由来共有の見せ方と参加意思の扱い。グループの作成・参加・閲覧範囲は2Cのグループ機能設計でも決める。会社固有の管理は2B応用時に扱う。
- 正常時、判断が曖昧な時、失敗した時の利用体験。
- 利用価値、記録品質、共有の正しさ、操作負担を何で評価するか。
- 比較対象、評価に用いる記録、成功条件と合格値。

## 完成条件

具体的な一場面をチームが再現でき、利用者の欲しい結果と検証する仮説を説明できること。成功条件がユーザーと合意され、未検証の結果を実証済みと扱わないこと。
